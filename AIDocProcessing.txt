SETUP | Upload Zone
Configuration &
Document Upload | The AI Document Processing workspace is activated inside the client's monthly Accounting Operations record. The officer sees 5 clearly labelled upload zones. Documents must be uploaded to the correct zone — the system rejects uploads to wrong zones based on file type and document analysis. Multiple files per zone are supported. There is no time limit on the upload phase. All upload zones are locked once 'Begin AI Processing' is clicked. | Accounting officer opens the monthly workspace in Accounting Operations Stage 3. All data has been confirmed received from client. | ZONE 1 — BANK STATEMENTS: All bank account statements for the month. Accepted: PDF (text or scanned), image. Multiple accounts = multiple files. ZONE 2 — SALES INVOICES: All invoices issued by the client to their customers. Accepted: PDF, image, Excel/CSV.
ZONE 3 — PURCHASE DOCUMENTS (Sub-categorised by officer): Trade Invoices / Utility Bills / Rent & Office Expenses / Staff & Payroll Expenses / Other Purchases. Officer tags each file with sub-category at upload.

ZONE 5 — PAYMENT GATEWAY STATEMENTS: Stripe, PayTabs, Telr, Noon Pay, or other payment gateway transaction exports.

S2 | Bank Statement
Ledger Construction
& Balance Validation | Bank statement data is processed first and becomes the master ledger for the entire reconciliation. Every bank transaction becomes a ledger row. The system validates the mathematical integrity of the statement: opening balance plus all credits minus all debits must equal the closing balance. Any discrepancy raises a DATA INTEGRITY WARNING that must be acknowledged by the officer before matching can begin. | Document ingestion complete (Stage S1) — bank statement(s) identified and raw data extracted. | 1. Parse all bank statement transactions into structured records: date, description, debit amount, credit amount, running balance, transaction reference (if present)
2. Handle multiple bank accounts as separate ledgers — officer can view per account or consolidated
3. Run balance validation: opening balance + SUM(credits) − SUM(debits) = closing balance
4. If balance does not validate: raise DATA INTEGRITY WARNING — show discrepancy amount and ask officer to acknowledge before continuing. Do not block processing — officer can proceed after acknowledgement.
5. Mark each transaction row: matched=false, match_confidence=null (default state before matching)
6. Build master ledger view for officer review | Relational database (transaction ledger table per client per month)
Balance validation logic (Node.js)

S4 | AI Matching Engine
— Automatic
Reconciliation | The matching engine attempts to link every bank statement transaction to a document from Zones 2–5. The engine uses a 6-level priority matching sequence. Each potential match is assigned a confidence score. The engine learns from officer corrections over time — for each client, successful manual matches are stored and used to improve future automatic matching. | Document data extraction complete (Stage S3) — all zones extracted and confidence-scored. | MATCHING PRIORITY SEQUENCE:
Level 1 — EXACT AMOUNT + DATE MATCH: Bank transaction amount exactly matches document total AND dates within 0 days. Confidence: 95–100%. Auto-match.
Level 2 — DATE RANGE + AMOUNT MATCH: Amounts match exactly, dates within 3 calendar days. Confidence: 85–94%. Auto-match.
Level 3 — REFERENCE NUMBER MATCH: Bank transaction reference number matches document number (invoice number, PO number, etc.). Confidence: 90–98%. Auto-match.
Level 4 — FUZZY NAME + AMOUNT MATCH: Bank transaction description fuzzy-matches supplier/customer name in document AND amounts are within 1%. Confidence: 70–84%. Suggest match (officer confirms).
Level 5 — AMOUNT + CATEGORY MATCH: Amount matches a document in the correct category. Confidence: 60–69%. Suggest match (officer confirms).
Level 6 — NO MATCH: Transaction cannot be matched. Goes to suspense. | Custom matching engine (Node.js backend)
Fuzzy string matching library (fuse.js or similar)

S6 | Suspense
Identification &
Categorisation | After the officer completes the reconciliation workspace review, the system compiles the final suspense list. Any bank transaction without a confirmed match and any document without a matched bank transaction enters the suspense list. Each suspense item is auto-categorised into one of 5 suspense types and pre-populated with client-facing instructions. | Officer clicks 'Generate Suspense Report' in Reconciliation Workspace. | 5 SUSPENSE TYPES (with pre-populated client instructions):
Type 1 — INCOME SUSPENSE: Bank credit with no matching sales invoice. Client instruction: 'We received a payment of [amount] on [date] from [description]. Please confirm: who paid this / what invoice this relates to / provide a copy of the invoice if available.'
Type 2 — EXPENSE SUSPENSE: Bank debit with no matching purchase document. Client instruction: 'We see a payment of [amount] on [date] to [description]. Please provide: supplier invoice or receipt for this payment.'
Type 3 — DOCUMENT SUSPENSE: Document uploaded but no matching bank transaction. Client instruction: '[Document type] from [supplier/customer] for [amount] dated [date] does not appear in your bank statement. Please confirm: was this paid by cash / a different bank account / is this document from a different period?'
Type 4 — AMOUNT VARIANCE: Bank transaction amount differs from document amount by more than 1%. Client instruction: 'The bank shows [bank amount] but the [document type] shows [document amount]. Please advise: is this a partial payment / bank charge / FX difference?'
Type 5 — GATEWAY SUSPENSE: Payment gateway transactions that cannot be reconciled with bank statement or sales invoices. Client instruction: '[Gateway] shows a transaction of [amount] on [date] (Ref: [ref]). Please confirm what this relates to.', | Relational database (suspense records table — per item: suspense type, transaction details, document details, client instruction text)
